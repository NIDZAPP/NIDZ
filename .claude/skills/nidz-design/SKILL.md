# Nidz Design — v1.7 workflow / v1.4 visual baseline

Read `NIDZ_DESIGN_SYSTEM.md`, **starting with §0.2 (Nidz 1.7 workflow) and §0.1 (Nidz 1.4 baseline)** and then the relevant product/trust sections. Historical visual prescriptions in §0.0 and elsewhere describe the previous implementation; §0.1 supersedes them for the 1.4 redesign.

## Always preserve

- Nidz's real brand name/logo and teal `#0F766E` + terracotta `#A84F32` as recognizable color anchors. Consult `nidz-color-guardian` on color changes.
- Product truth, privacy, safety, trust provenance, accessibility, mobile usability, multilingual French/English/Arabic and RTL.
- Existing user journeys and functionality unless the task specifically authorizes product changes.
- No fake verification, testimonials, ratings, payments, insurance, bookings, availability or cross-user communication.

## Creative freedom (v1.4)

- **Do not preserve old layouts, font choices, radii, cards, whitespace or animation rules solely because they exist.** The old UI is not the quality standard.
- Pill-shaped main/secondary action buttons are an approved global direction; maintain clear action hierarchy and comfortable touch targets.
- Seek a distinct, polished, warm, mobile-first design with intentional compositions, typography, imagery, surfaces and restrained, useful motion.
- Use HaHo through Figma MCP **only if access is verified**; it is inspiration, not an authority or a license to copy. Use Impeccable as design lead and emil-design-eng as interaction lead; narrower skills support them only when relevant.
- A full visual reinvention is allowed; a product rewrite, fake functionality, accessibility regression or unapproved brand-color replacement is not.
- Prefer semantic design tokens and reusable patterns. Document deliberate palette-role changes and consult the color guardian for a scoped evidence-based review; ordinary aesthetic decisions within the authorized scope need no additional user approval. Changing the brand anchors requires explicit user authorization.

## Working method

Inspect the existing screen → establish direction with the primary skills → implement scoped aesthetic decisions autonomously when implementation is requested → document design-system changes → review real screenshots and interactions. Follow CLAUDE.md for approval boundaries and comp-led workflows. Clearly separate **implemented**, **user-approved**, and **proposed**. Never claim a design, test or Figma access was verified unless it was.
